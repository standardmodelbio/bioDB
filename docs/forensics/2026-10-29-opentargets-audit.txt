OpenTargets data and bioDB integration forensic audit
29 October 2026

The collected GWAS data survives locally and on Hugging Face. The main gaps are
integration and completeness: all-significant ingestion lives in hg-horizon,
BioDocs traits were merged into a feature branch, several bioDB modules remain
unmerged, and bioDB can silently accept an incomplete cache. No evidence was
found of a wholesale loss of the OpenTargets raw-fetch API.

This audit records the state found; it does not repair library code, merge
branches, refresh dependency locks, rerun bulk ingestion, or publish changes.
Recovery snapshots and reproducible checks are saved locally. Existing tracked
source and dirty work were preserved.

2. What all significant actually covers

The all-significant table was assembled from GWAS Catalog harmonized summary
statistics, with OpenTargets study/locus metadata defining the worklist. It is
not an OpenTargets output dataset called allsig. The source and fine-mapping
products should retain distinct provenance.

The published pipeline selects +/-1 Mb windows around OpenTargets lead loci.
build_allsig_worklist.py creates those windows; reconcile_allsig.py continues to
apply the region filter even when downloading a whole summary-statistics file.
Therefore the published table cannot establish genome-wide significant-variant
coverage outside the selected windows. An indexed query returning no significant
rows in those windows is not proof that the study has no hits anywhere.

The final published missing-study report contains 679 entries:
  372 no_genomewide_sig
  249 no_sig_in_region
   44 download_failed
   14 unparseable_header
These are pipeline labels; in particular, the regional labels do not establish
globally empty studies.

A separate genome-wide fetch_allsig_genomewide.py is committed in hg-horizon,
including history a479fa2/2f660e3 and current codex/dna-landscape-export. No
published output lineage was found for that alternative. Its URL assumptions,
fixed-column parsing, positive-SE/nonzero-p filters and failure-to-empty behavior
need review before using it to claim complete coverage.

The 104M export has pip entirely null and does not retain p-values/z-scores as
columns. Published rounded statistics include 3,766 zero SE values and 2,999 zero
beta values. Reconstructing exact z-scores or p-values from that export is not
equivalent to recovering the original summary statistics. Preserve raw columns
and log-p values in any replacement ingestion.
The deployed HF ingest/fetch_allsig_sumstats.py blob a4d2e21475189b251fd04311f6b12af780d72361
is not found among local Git/ref/reflog paths; its exact historical source was
copied into the evidence directory. It rounds beta/SE/z to four decimals during
ingestion, so even retained ingestion shards may already have lost precision.
The archived HF Harvest fetch source also differs from the newer untracked local
source. Those remote snapshots preserve another part of the implementation history.

  biodb.opentargets.studies.get_study
  biodb.opentargets.studies.attach_study_type

Existing generic calls for all trait and drug records:
  from biodb import opentargets as ot
  traits = ot.get_dataset("disease", version="25.12")
  drugs = ot.get_dataset("drug_molecule", version="25.12")

The dataset is drug_molecule, not drug. There are no get_traits/get_diseases/
get_drugs convenience functions. History and BioDocs callsites did not identify
such functions as removed dependencies; BioDocs delegates to get_dataset.

For nested fine-mapping input, get_dataset("credible_set") retains raw locus
members. ensure_cached_shards("credible_set") supplies paths for a lazy/streamed
projection. The convenience get_credible_set() drops the locus column and emits
one row per credible set; it is not an all-member variant reader. Its force-free
signature also means cache repair must currently be performed separately.

There is no bioDB wrapper for hg-horizon's published allsig artifact, nor a
reusable bioDB GWAS Catalog all-significant acquisition pipeline. This code was
never integrated into bioDB; it is recoverable in hg-horizon scripts. A generic
OpenTargets dataset downloader alone does not fulfill that requirement.

OpenTargets variants/studies were merged in bioDB PR #35:
  https://github.com/standardmodelbio/bioDB/pull/35
  664138552df917db110b3351f6898785d51ed25f
The former opentargets.py moved verbatim to opentargets/_bulk.py and its names are
re-exported from the package. This was a file move, not disappearance of the
bulk implementation.

4. Confirmed current OpenTargets defects

A. Partial caches silently look complete
  src/biodb/opentargets/_bulk.py:368-370 returns any cached *.parquet files before
  consulting the remote shard list. limit_files=1 followed by an unlimited call
  therefore keeps returning one shard. A synthetic real-Parquet probe reproduced
  this with returned_files=1 and manifest_calls=0. The remote_url path in
  get_dataset has the same behavior.

  Actual incomplete caches verified against live EBI listings:
  Release/dataset                       Local/upstream   Missing
  25.12 evidence_gwas_credible_sets         1/33             32
  25.12 evidence_europepmc                  1/200           199
  25.12 evidence_uniprot_variants           1/8               7
  25.12 literature                         1/334           333
  25.12 enhancer_to_gene                   1/83             82
  26.03 association_overall_indirect        1/143           142

  evidence_gwas_credible_sets is gene-disease evidence, distinct from the
  complete 200-shard credible_set collection above.

B. A truncated file is treated as cached data
  25.12/enhancer_to_gene/035a1aa5-7ee1-4891-a078-12ee29406b1f.parquet
  is exactly 15,728,640 bytes and fails Parquet footer validation.
  _download_to_cache accepts existing files by existence; _downloads.stream_to_file
  writes directly to the final filename. Interrupted transfers can leave files
  in this state. That is a code-supported failure mechanism, not proof of the
  historical cause of this particular truncated file. No cache files were
  removed or repaired during the audit.

C. Lead variant and returned PIP can identify different variants
  src/biodb/opentargets/variants.py:68 takes locus[0].posteriorProbability but
  retains top-level variantId. A real first-shard example:
    studyId        GCST90662908
    row variantId  1_3410468_C_T
    PIP variantId  1_3411057_CAT_C
    returned PIP   0.10255448794673071
    locus members  28
  This caveat is documented, but callers can still pair a lead beta/coordinate
  with another member's PIP. hg_horizon/sources.py:94-135 uses beta*PIP for event
  weights. A correct lead reader must match by variantId; an all-member reader
  must explode locus and retain each member's own statistics and membership flags.
  The full-cache scan found this mismatch in 677 raw GWAS rows and 574 retained
  browser-export rows. The smaller browser table is explained by significance
  filtering (1,354,216 rows/51,694 studies), then positive |beta|*first-PIP
  (1,293,167/48,341). No canonical-chromosome rows are removed at that point.
  Correct member-level transforms already exist outside bioDB:
    hg_horizon/functional.py:135 explode_credible_sets
    hg_horizon/locus_grid.py:132 explode_locus_with_effect
  The latter retains each member's own beta/SE. Reuse these data-shaping lessons
  instead of applying one lead effect to every exploded member.

D. Package default reassignment stopped propagating after the package move
  The documented ot.DEFAULT_GENE_ASSOCIATION_DATASETS=['known_drug'] assignment
  does not affect _bulk's function globals. The probe resolved the original six
  datasets. Explicit datasets= and the environment override remain available.
  Existing tests patch _bulk directly and miss the documented public assignment.

E. README targeted-query imports are incorrect
  README.md:89 imports query_target/query_disease from biodb.opentargets, which
  does not export them. Actual implementation is biodb.opentargets_graphql.
  All four existing live GraphQL query tests passed with network access.
  This is a documentation/API discoverability problem, not absent query code.

7. Recovery and implementation order

1. Preserve current evidence before branch cleanup. Verified complete-history
   bundles for bioDB's celltype branch and hg-horizon's current refs are saved.
   BioDocs trait patch and untracked Harvest archive are saved with checksums.
2. Fix bulk cache semantics first: pinned-release manifests, missing-shard repair,
   explicit partial/full state, atomic temporary downloads and Parquet validation.
   Cover preview-then-full, interrupted transfer and resume with regression tests.
3. Add an all-member credible-set reader with correct variant-specific PIPs,
   beta/SE/p-values and 95/99 flags. Correct lead lookup without silently changing
   the historical reader's row unit. Provide lazy/batched processing for large data.
4. Add discoverable all-traits/all-drugs wrappers or entity readers over disease
   and drug_molecule; document raw retrieval separately from BioDocs corpus building.
   Repair README imports and package-level configuration semantics.
5. Integrate a GWAS Catalog summary-statistics module into bioDB, reusing the
   validated hg parser/reconciliation pieces. Keep region-scoped and genome-wide
   modes explicit; report per-study coverage/failures and preserve original/log-p
   statistics. A pinned hg artifact reader can expose existing data separately.
6. Integrate BioDocs #104 onto current main and use a current checkout for drugs.
   Rebuild affected bibliography/joins only after complete inputs are verified.
   Refresh bioDB pins deliberately and validate adapters against the chosen SHA.
7. Rebase/integrate celltype work and its local-only count change with tests/docs.
   Review Harvest independently; its unfinished run should not supply a completeness
   claim or be relaunched implicitly as part of this investigation.
